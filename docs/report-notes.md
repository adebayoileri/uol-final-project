  - **Structured LLM output for education** (Phase A): Recent work (e.g. Borchert et al. 2023 on "CoT prompting for structured quiz generation") shows that schema-constrained prompts substantially improve coherence of LLM-generated educational content. The Phase A prompt design — requiring `key_concepts`, `worked_example`, `common_pitfalls`, `practice_prompts` per lesson — follows this structured-output paradigm rather than free-form generation.

  - **Gamification in education** (Phase G): Achievement systems (badges, streaks) draw on self-determination theory (Deci & Ryan) and are extensively studied in gamified learning (Hamari et al. 2014 meta-analysis). The Phase G achievement engine implements four achievements aligned with effort (question_master), consistency (consistent_learner), mastery (memory_master), and completion (course_champion).
  - **Spaced repetition mastery tracking** (Phase G2): The FSRS stability parameter (days until 90% retention) provides a principled mastery signal. The formula `min(1.0, stability/30)` maps this to a 0–1 scale where 30 days ≈ full mastery. This is distinct from simpler pass-rate metrics and aligns with the FSRS paper's notion of retrievability.
  - **Learning analytics and study time optimisation** (Phase H): The field of learning analytics (Siemens & Long 2011) proposes that time-of-day performance data can inform personalised scheduling. The Phase H optimal study time implementation is a lightweight version of this — using answer score × hour buckets rather than requiring a full user model.

- 2026-07-19 IA rationale (R3). The five-destination IA (Home / Course library / Course home / Lesson view / Review session) separates two cognitively distinct activities: encoding (reading a lesson, generating questions) and retrieval (FSRS review). The old single-page course view conflated both, making it impossible to scope the review queue to a single course. The key IA decisions were: (1) one lesson per page — prevents cognitive overload and enables per-lesson completion tracking; (2) course home as navigation hub, not content — all learning happens in dedicated sub-pages; (3) review as a named destination with a dedicated route, not a popup — signals that review is a first-class activity, not a footnote; (4) course_id on cards and questions (denormalised) — the data model follows the IA rather than forcing the IA to work around the data model.

- 2026-08-09 Design additions for Phases A–I:
  - **Prompt-as-file pattern** (Phase A): Prompts extracted to `backend/app/prompts/*.txt` and loaded at module-level. Rationale: separates template content from Python logic; enables A/B testing by file swap; makes diffs readable as prose.
  - **Parser-first structured content** (Phase A2): `parse_lesson_body(raw) -> dict` always returns known keys (empty defaults). Downstream code never has to handle `KeyError` on missing fields from a bad LLM generation. `is_structured: bool` flag enables graceful fallback to plain-text rendering in the frontend.
  - **JSON lesson body, not markdown** (Phase A): Decision to keep lesson body as embedded JSON (rather than markdown) in the `description` column avoids a separate storage table for structured content. The content_parser handles extraction; the frontend has a JSON-first path with markdown fallback.
  - **Progressive rendering strategy** (Phase B): LessonView tries to JSON-parse the description; if it succeeds, renders key_concepts as cards, worked_example as pre block, pitfalls as Callout components. If it fails (legacy plain text), falls through to `LessonRenderer` (react-markdown). No migration required.
  - **Streaming chat via SSE not WebSockets** (Phase E): FastAPI's `StreamingResponse` with a sync generator avoids any async conversion. SSE is simpler than WebSockets for unidirectional server→client streaming: no connection management, native browser support, reconnection built in. The `useSSE` hook uses the `ReadableStream` API for zero-dependency streaming.
  - **Best-effort instrumentation** (Phase F): `record_event` never raises — any DB error is logged and the request proceeds normally. This was the critical design choice: event recording is observability infrastructure, not part of the application correctness invariant. Tests that don't set up the event tables pass unchanged.
  - **Mastery formula: stability/30** (Phase G2): Documented in decisions.md. FSRS stability is the number of days until 90% retention. A card with stability=30 days is reviewed monthly with high recall confidence — we define that as "full mastery". The formula produces a 0–1 scale that reads naturally as a percentage.
  - **Certificate via WeasyPrint** (Phase G3): WeasyPrint converts HTML+CSS to PDF in-process — but see 2026-08-18: this framing is what hid a hard dependency on Pango/GLib/cairo, and the renderer is now fpdf2. The template uses simple `{{ }}` string substitution (not Jinja2) to keep the certificate service self-contained. Cached by `mastery_snapshot`; regenerates if mastery changes >5%.
  - **Timeline uses existing `duration_minutes`** (Phase I): No new column added. The plan considered adding `estimated_minutes` but `duration_minutes` already carries this semantic from course generation. Avoiding unnecessary schema additions is a cross-cutting rule in this project.

- 2026-07-19 Restructure decision: denormalised course_id vs. join-time derivation. Adding course_id as a column on questions and cards (R1) rather than deriving it at query time (3-hop join: card → question → lesson → module → course) was a deliberate trade-off. The join approach is pure but slow for the review query pattern where we need to filter by course_id in `ORDER BY due LIMIT 1`. The column + composite index `(course_id, due)` gives O(log N + k) for the common case. Backfilling existing rows via UPDATE … SELECT ensures no data migration downtime.

- 2026-08-09 Methodological note discovered during the redesign — the frontend typecheck used throughout the project, `npx tsc --noEmit`, was a vacuous pass. - 2026-08-15 Lesson content depth — root cause, fix, and measured effect. Final pre-submission review flagged that generated lessons were shallow: a lesson page showed its title, objectives, a two-sentence paragraph, and nothing else. The cause was a single line. `app/routes/courses.py:80` persisted `lesson_data.get("description", "")` — the prose summary alone — while `app/prompts/course_structure.txt` explicitly asks the model to emit four further fields per lesson (`key_concepts`, `worked_example`, `common_pitfalls`, `practice_prompts`) as *siblings* of `description`. Those fields arrived in the parsed response and were silently discarded at persistence time. Because `content_parser.parse_lesson_body()` returns early unless its input begins with `{`, it had therefore always reported `is_structured=False`, which made **five separate consumers dead code**: the structured renderer in `LessonBody.tsx` (the key-concept cards, worked-example block and pitfall callouts had never once rendered), the narration builder's key-concepts branch, the tutor chat's grounding context, the question generator's `key_concepts_block` and `practice_prompts_block`, and the J1 content-quality evaluation. Measured on the live database before the fix: **19 lessons, 0 containing structured content, mean description length 98 characters, longest 264**. The producer and the consumers had both been written to a structured contract; only the storage layer between them had not, so the whole feature had been inert since it was introduced.

- 2026-08-15 Why the fix is two-pass rather than one-line. Restoring the discarded fields alone would not have produced deep content, because a single `POST /courses` call must emit every lesson in the course — up to 50 for a long-term course — and therefore rations one output budget across all of them. Generation was split: course creation keeps its single fast call and stays deliberately shallow (titles, prose summary, objectives), and a second prompt generates the body for one lesson at a time, on first open, cached in a new `lessons.content_json` column. Each lesson consequently receives an entire context window rather than a fiftieth of one. **Measured on a real lesson: a 30-character description ("Content for open() and read()") produced 2,082 characters of structured content in 17.3 seconds** — three concepts each with a runnable code example, a 707-character four-step worked example, and two specific pitfalls. Round-trip through the API: 10.4 s to generate, 0.018 s on the cached second request. A deliberate secondary benefit of the lazy trigger is that the 19 pre-existing shallow lessons enrich themselves as they are opened, so no backfill script or regeneration was required. An `_validate_content()` gate (≥2 concepts, one definition ≥60 chars, worked example ≥200 chars, retry once) rejects output that satisfies the JSON schema but is shallow — this is what prevents the original defect from silently returning.

- 2026-08-15 Narration scope narrowed to lesson body only. Narration previously opened with `"Lesson: <title>."`, then recited every learning objective, then spoke the literal section headers `"Key concepts."` and `"Worked example."` before any actual content. It now reads only substance: the prose summary, then each concept as a natural sentence pair (`"open(). Returns a file object…"` rather than a heading read aloud), the concept's example, the worked-example steps, and the pitfalls. Practice prompts are excluded deliberately — read aloud with no pause for an answer they only confuse. Because the narration cache key is a SHA-256 of the narration text, changing the builder invalidates every cached WAV automatically and each lesson regenerates once on next play. Two robustness gaps were closed at the same time: `_chunk_text("")` returned `[""]`, which would have handed the speech synthesiser an empty argument, and the endpoint now returns 422 for a lesson with nothing to narrate rather than surfacing a subprocess error as a 503.

- 2026-08-15 Downstream consumers verified rather than assumed. The question generator and the tutor chat both had correct enrichment wiring that had never executed. The tutor's worked-example truncation was raised from 400 to 1,200 characters (at 400 a genuine four-step example is cut off after step one) and its overall context cap from 2,000 to 4,000, with an explicit `num_ctx: 8192` — without it the enlarged system message would overflow Ollama's default window, and overflow evicts from the *start* of the prompt, exactly where the lesson grounding sits. That failure would have left the tutor looking grounded in the code while being ungrounded at runtime.

- 2026-08-15 Evaluation-validity correction. `eval/j1_content_quality.py` computed its coverage figure by calling `json.loads()` on the prose `description` and reading the four structured fields out of the result. - 2026-08-16 AI tutor retention defect — a streaming/render race. The tutor rendered its reply token by token and then discarded it the moment the stream finished, so no exchange ever remained in the transcript. The backend was verified sound first: the endpoint emitted 23 SSE lines ending in `[DONE]` and wrote both the user message and the complete assistant reply to `lesson_chat_messages`, confirming the fault lay in the client. In `AIAssistantPanel`, tokens accumulated into React state which a `useEffect` mirrored into a ref, and the completion handler read that ref to commit the message. But the SSE reader invokes its token and completion callbacks synchronously while draining one network read, whereas an effect body does not run until the current task yields — and the measured reply arrived in roughly 1.3 seconds, entirely within a single read. The ref therefore still held its initial empty string at commit time, so the message was stored empty while the live buffer was simultaneously cleared. The fix makes the ref the authoritative accumulator, written synchronously as each token arrives, with React state retained only to drive re-rendering. Finalisation also moved from the `[DONE]` handler to the point where the stream promise resolves, since that covers every terminal condition including a connection dropped mid-reply; and the empty placeholder bubble is now discarded rather than committed when nothing arrives, which previously would also have been replayed as context on the following turn. The failure was reproduced deterministically outside React — modelling only the callback ordering and effect timing against the reader's own parse loop — where the original strategy returns an empty string and the corrected one returns the full reply. Worth recording in the evaluation chapter as an instance of a defect that is invisible to unit testing and to type checking: every function behaved correctly in isolation, and the bug existed purely in the interleaving between them.

- 2026-08-16 Review restructured from a single pile into a course picker. `/review` previously ran one session across every course's cards at once, ordered by due date, with no course grouping and no way to tell which course a card belonged to — `CardResponse` did not carry a course at all, so the interface physically could not say. There was also no endpoint that listed cards: `GET /review/next` returned exactly one, and `course_id` was its only filter. `/review` is now a hub showing per-course due counts with date filters, and the session moved beneath it. Filtering covers both when a card was **created** (`cards.created_at`, a real DATETIME, previously unindexed) and when it falls **due** (`cards.due`, TEXT ISO-8601, so the range comparison is lexicographic — valid only because every value is normalised UTC ISO, the same assumption the existing `Card.due <= now_iso` check already relied on). The load-bearing property is that the hub, the queue and the session all filter through one shared helper: if the hub aggregated differently from the session it launches, the count shown before starting would be a lie, and there is a test asserting the two are equal under the same filter. A dedicated `/review/courses` endpoint was added rather than reusing `GET /courses`'s existing per-course `due_now`, because that summary takes no filter arguments and so cannot answer the filtered question at all.

- 2026-08-16 Practice restructured around courses, and extended to cover VARK. The pronunciation drill drew its phrases from five hardcoded Spanish strings at a standalone `/pronunciation` route, offered identically to every course — a chess course was invited to practise Spanish, while the Spanish course got nothing from its own material. Practice is now course-scoped (`/practice` → `/practice/:courseId` → the drill) and four new drills were added so that the modalities beyond read/write are represented: **multiple choice** (read/write), **concept match** (visual), **step ordering** (kinesthetic) and **listening** (aural), with pronunciation gated to language courses. The design decision that makes this affordable is that **every drill is a pure function of the already-stored `content_json`**, with no LLM call when a learner starts one: they are instant, deterministic, work with Ollama stopped, and are testable without stubbing a model. Drills record a completion event so they feed streaks and achievements, but deliberately do not touch FSRS — practice is not scheduled review, and folding it into the scheduler would corrupt the stability estimates the review system depends on. Because drills need enriched lessons and only 3 of 19 are enriched today, unavailable drills are rendered **disabled with the specific reason and an enrichment progress bar** rather than hidden; hiding them would make a course look broken rather than not yet ready.

- 2026-08-16 Two live defects found by testing branching logic against real data rather than fixtures. Both came from the same root cause: `Course.category` is free text typed into a plain input, and two features branched on it alone. `_detect_lang` tested for `"spanish"` in the category, but the Spanish course was filed under `"Language"` — **so the Spanish course had been narrated in an English voice**. `_is_python_lesson` required the category to equal `"python"` exactly, but the Python course was filed under `"Programming"` — **so it had never once received the fill-in-the-blank code exercises the feature exists to provide**, despite "Python" appearing in both its goal and its title. The general point for the evaluation chapter is that neither bug was reachable by any unit test written against fixtures, because the fixtures encoded the category values the developer *expected* rather than the ones the application had actually stored.

- 2026-08-16 A third instance of the same class of defect, in the ordering drill. `lesson_content.txt` instructs the model to separate worked-example steps with a newline; checking the live database, **all three enriched lessons instead returned one continuous line** of `"Step 1: ... Step 2: ..."`. Splitting on newlines therefore yielded a single step every time, and the kinesthetic drill reported itself permanently unavailable for content that visibly contained four steps. The splitter now falls back to `Step N:` markers and numbered prose. Tightening the prompt was rejected as the primary fix: the parser must tolerate what the model actually emits, and a prompt cannot be trusted to hold a format it has already been asked for once and ignored. This is worth stating alongside the two category bugs — three defects in one session, all invisible to a green test suite, all found only by running the code against real stored content.

- 2026-08-17 Authentication and per-user data isolation. The application had no notion of a user: a repo-wide grep for `auth|login|jwt|password|current_user` returned zero matches, and every route served every row in the database to anyone who could reach the port. Misleadingly, three tables were *named* `user_events`, `user_achievements` and `study_sessions` while having no user column at all. Added registration, login, logout, session management and full data isolation, then assigned all pre-existing data to a seed account. **The mechanism was chosen by a constraint rather than by preference**: a JWT in `localStorage` is the conventional choice, but `/audio/{filename}` is consumed by `new Audio(...)` and the certificate by a blob fetch, and a browser-issued media request cannot carry an `Authorization` header — a bearer scheme would have required signed URLs or rewriting both media paths. An `HttpOnly` session cookie is sent automatically by those requests (same-site across ports, so `SameSite=Lax` permits it), so the media paths needed zero frontend changes. Passwords use stdlib `hashlib.scrypt` at OWASP's floor parameters rather than bcrypt or argon2id: memory-hard, no compiled wheel to fail on a marker's machine, and stored self-describing as `scrypt$n$r$p$salt$hash` so a rehash-on-login upgrade remains open.

- 2026-08-17 The ownership model, and its honest limitation. `Course` is the root of a strict tree with single-valued foreign keys throughout, so `user_id` was needed on only **four** tables — `courses` plus the three with no path to a course. Everything else (chat transcripts, narration cache, certificate cache, embeddings, questions, cards) is owned transitively. `cards` was deliberately not given a denormalised `user_id` despite already carrying a denormalised `course_id`: a join cannot be wrong, a copied column can, and the existing denormalisation already needs a drift-repair script. This is a **single-owner-per-course** model, not enrolment — `lessons.completed_at` living on the shared content row is exactly what makes it single-tenant, and supporting a course shared between learners would require an `enrolments` join table plus moving all per-user progress out of the content tree. That is a restructure rather than an addition, and is worth stating as future work rather than implying the design generalises.

- 2026-08-17 Three pre-existing defects that only multi-user use would have exposed. (i) `user_achievements.achievement_id` carried a **globally unique** constraint, so the first user ever to unlock an achievement would permanently block every other user — and because the achievement engine swallows exceptions, the failure would have been completely silent. Rebuilt with `UNIQUE(user_id, achievement_id)` and a matching `ON CONFLICT` target. (ii) `record_event` upserted the "current study session" by selecting the single most recent row across the whole table within a ten-minute window, so two users active concurrently would have merged into one session, inflating both users' study time. (iii) `GET /search` returned `content_text` for every embedding in the database — full lesson prose — requiring **no id guessing at all**. That last one was the highest-severity gap and was not on the list produced by reading the route table; it surfaced only when auditing which queries had no filter rather than which routes took an id.

- 2026-08-17 The evidence artefacts. Two tests were written to be citable rather than merely passing. `test_route_coverage.py` walks `app.routes` and asserts the auth dependency appears in every route's dependency tree bar an explicit exempt set — a stronger claim than enumerating today's protected routes, because it also holds for routes added after the audit. `test_isolation.py` registers two real accounts with real session cookies against one database (a separate `TestClient` each, since each keeps its own cookie jar) and runs a parametrised matrix across 14 cross-user routes plus the shape-different cases: an empty list rather than a 404 for `GET /courses`, a 204 rather than another user's card for `GET /review/next`, an empty result for a search on a term unique to the other user's content. **Running that matrix immediately caught three real leaks the manual enumeration had missed** — `/courses/{id}/mastery` and `/courses/{id}/certificate` both performed unscoped lookups, and `GET /achievements` returned every user's unlocks to everyone. The most important assertion in the file is not the status code but the one after it: following a rejected `POST /lessons/{id}/complete`, the row is re-read to confirm `completed_at` is still NULL, because **a 404 returned after a write is concealment, not isolation**.

- 2026-08-17 Migration and adoption. SQLite cannot add a `NOT NULL` column to a populated table, and a twelve-step table rebuild was judged the riskiest possible change to attempt in submission week for no user-visible gain. The constraint is therefore split: the column is nullable at DDL level, the ORM declares it non-null, and `create_all` gives every fresh installation the real constraint — and since `*.db` is gitignored, every clone *is* a fresh installation. `scripts/seed_user.py` adopts the legacy rows, guarded by `WHERE user_id IS NULL` so it is safe to re-run and a no-op on a new database. Verified against the live data: 5 courses, 21 events and 6 study sessions adopted, 0 orphans remaining, second run adopts 0. The password comes from an environment variable passed inline and the script exits non-zero without it — notably **not** from `backend/.env`, because nothing in this project loads dotenv, which would have produced a script that always refused to run.

- 2026-08-17 Test suite grew 240 → 309. The enabling change came first: there was no `conftest.py`, and all 16 test files built their own client fixture, so gating the routers would have 401'd every existing test. One autouse fixture overriding the auth dependency on the app object reached all of them without edits. Beyond the two evidence artefacts, `test_auth.py` covers registration, duplicate-email rejection across case and whitespace variants, byte-identical responses for wrong-password versus unknown-email, cookie flags asserted on the raw `Set-Cookie` header, and expired and revoked session rejection. - 2026-08-17 Light and dark theme, added without touching the dark one. The application was dark-only: a single `@theme` block, `color-scheme: dark`, hardcoded meta tags, and zero occurrences of `matchMedia` or `dark:` in the whole of `src/`. The conventional Tailwind route — a `dark:` variant on every colour-bearing class — was rejected because it inverts the default, making dark the exception written across 300+ call sites with no way to prove none were missed. Instead dark stays in `@theme` as the bare `:root` default and light is applied purely as an override, through a media query for following the OS and a `data-theme` attribute for an explicit choice. **Two properties were verified against the compiled stylesheet before the approach was committed to**, since the entire plan rests on them: opacity modifiers compile to `color-mix(in oklab, var(--color-success) 12%, transparent)`, so retuning a hue per theme reaches all ~67 tint sites without editing a single className; and tokens land on `:root,:host` as plain custom properties with no `@theme inline`, so an attribute selector wins on specificity. The claim that dark is unchanged is likewise checked rather than asserted — diffing the compiled custom-property block against a build of the pre-theme commit gives **105 retained tokens and 0 changed values**, with three vars disappearing only because Tailwind prunes vars whose classes were renamed to identically-valued tokens. This matters practically, not just aesthetically: every screenshot already in the report is dark.

- 2026-08-17 Two silent theme defects, one root cause: `@theme` resolves at build time. The light palette shipped `--shadow-e1..e4` overrides that turned out to be **dead CSS**. Tailwind inlines a `--shadow-*` theme value into the utility, so `shadow-e1` compiles to `.shadow-e1{--tw-shadow:0 1px 2px var(--tw-shadow-color,#0006);…}` and no `var(--shadow-e1)` survives into the output for a theme to override — light mode would have painted the dark theme's 40–70% black shadows onto a white canvas. The same class of problem hit the logo by a different route: its gradient ran `brand-400 → brand-600`, but light deliberately retunes the upper brand ramp downward so brand-coloured *text* stays legible on white, which moved `brand-400` onto exactly `brand-600` and collapsed the tile to a flat fill that no longer matched `favicon.svg`. Both are now plain `:root` custom properties with hand-written utilities, keeping the `var()` reference alive at runtime. Worth recording because of **how** these failed rather than that they did: neither breaks a build, throws, or fails a type check — the page renders, it just renders wrong, and only in the theme the developer was not looking at. The transferable point is that "I overrode the token" and "the override has an effect" are separate claims, and only the compiled stylesheet distinguishes them. This is the fourth defect this project has surfaced by inspecting real output rather than trusting the source to mean what it says.

- 2026-08-17 The parts of a theme that a token swap cannot reach. Roughly a dozen sites were dark-only in ways no palette override touches, and each fails differently. The skeleton shimmer was `rgb(255 255 255 / 0.045)` baked into an arbitrary class — invisible on a light surface, so **loading skeletons would silently stop animating** while remaining present. Nine `text-white` on brand fills were correct but could not simply be swapped to `text-fg`, since the brand fill stays saturated in both themes; they became `text-on-brand`. Two display headings used `bg-clip-text text-transparent`, which has no fallback colour at all, so a clip failure yields invisible text; they now carry a real `text-fg` underneath. The review heatmap ramped `brand-900 → brand-500`, which **inverts perceptually on light** — the emptiest cells become the darkest — so it moved to `--color-heat-1/2/3` and ramps the correct direction in each theme. The `prefers-contrast: more` block also had to be split per theme, because raising contrast moves values in opposite directions depending on which theme is active. Recording these separately from the palette because they are the difference between a theme that is *designed* and one that is merely *inverted*, and because most of them fail quietly rather than visibly.

- 2026-08-17 Anti-FOUC and the login-page trade-off. A blocking inline script in `<head>` reads the stored preference and sets `data-theme` before first paint; React's lazy `useState` initialiser is too late, since it runs after the HTML parses, so without the script the wrong background paints first on every load. The preference persists under a bare `theme` key rather than a user-namespaced one, deliberately — the login page renders before a `user` exists. The appearance control itself lives in a new `UserMenu`, as a three-option radiogroup rather than a two-state toggle, so that "follow the OS" stays reachable after a user has overridden it; a plain toggle would pin them to an explicit choice permanently. **The accepted cost is that the menu is auth-gated, so there is no toggle on the login screen** — a signed-out user still gets the correct theme from the OS default, but cannot override it until signed in. Stated here rather than glossed, since it is a real limitation of putting the control behind authentication.


- 2026-08-17 The light palette was checked by measurement, not by eye. The plan flagged the main tuning risk explicitly — "too pale and the 67 tints vanish, too saturated and the UI shouts" — so rather than judging it visually, WCAG contrast ratios were computed for 16 foreground/background pairs actually used in the interface, across **four** rendering states: dark, light, and each under `prefers-contrast: more`. This caught two genuine failures that looked perfectly acceptable in a screenshot. `--color-success` at `#059669` gives only **3.77:1** on white — below AA for body text — which matters because success is the colour of a correct-answer verdict, the single most-read status in the review flow; it moved to `#047857` (5.48:1). And `--color-fg-faint` sat at 3.38:1 in light against 3.60:1 in dark, so light was quietly *worse* than the theme it was modelled on; it moved to 3.74:1, parity with dark. The audit also exposed a **pre-existing** gap neither theme had: `fg-faint` is AA-large-only in both, and the `prefers-contrast: more` block overrode `fg-muted` and `fg-subtle` while omitting `fg-faint` entirely — so the users who had explicitly asked the operating system for more contrast were the ones not getting it on the lowest-contrast token in the palette. Adding it to all three high-contrast blocks brings every measured pair to AA in both themes when contrast is requested. Worth reporting because the finding is not "the colours were wrong" but that **a palette's accessibility is a property you can compute, and computing it found things that reviewing it would not** — the same pattern as the category and shadow defects, applied to design rather than logic.

- 2026-08-17 Lesson diagrams, and why no image model was involved. Lessons were text-only, so a chess lesson described the knight's move in prose. The brief asked for SVG and animation rather than pictures, and the first finding was that the image-model work believed to exist had never reached the repository at all — an exhaustive sweep of source, `uv.lock`, every branch, the full history and the stash list found nothing, and `docs/future-work.md` had already recorded image generation as cut from scope. That turned out to be irrelevant, because **the feature needs no image model**. The text model emits a structured specification and hand-written renderers draw it: it names one of four kinds (`board`, `graph`, `plot`, `geometry`) and fills semantic fields, and code derives every coordinate. Model-authored SVG was rejected on four independently sufficient grounds — an 8B model cannot place 64 `<rect>` elements reliably and a single wrong coordinate still parses; `react-markdown` here ships without `rehype-raw`, so rendering markup would have introduced both the app's first HTML-injection surface and its first sanitiser dependency; a model writes `fill="#f0d9b5"` where the app needs `var(--color-brand-500)` to resolve in two themes; and SVG's own `<animate>` is untouched by the `reducedMotion` configuration that governs everything else. The same bargain the drill system already makes — deterministic rendering from stored content, no model call at draw time — extended to pictures.

- 2026-08-17 The validator is the feature, and its rule is "reject false claims, repair presentation". A generated diagram can be imperfect in two quite different ways, and treating them alike is what makes this kind of feature either useless or dangerous. **Claims about the world are rejected**: an edge to a node that does not exist, a triangle whose sides cannot close, an inverted axis range, a step referencing an element absent from the diagram — that last one being the single check that stops an animation from playing and highlighting nothing. **Choices about presentation are repaired**: a `tree` layout whose data is not a tree, or a `chain` whose data branches, downgrades to `layered`, which draws both correctly; an over-long label is clipped rather than thrown away, since the renderer truncates far below the cap regardless. **Unknown keys are ignored**, because a small model routinely adds a stray `"notes"` and discarding a sound diagram over one trades a real diagram for none. The asymmetry underneath all three is that a missing diagram is invisible while a wrong one teaches something false, so the validator errs strict on truth and forgiving on form.

- 2026-08-17 A fourth defect found by running against real data rather than fixtures — and the most instructive of them. Generating for the live Chess Fundamentals course produced a bishop on e2 highlighting a1, h8, a8, h1, c4 and f5; **only c4 is on a diagonal**. Every one of those is a legal square, so nothing structural rejected it: the spec was well-formed, drawable, plausible, and a completely false account of how a bishop moves. It is worth stating exactly why this got through, because the reason is more interesting than the bug. The design's whole premise is that *the model returns meaning and code computes geometry* — and which squares a piece can reach **is** geometry. The failure was not a flaw in the principle but an incomplete application of it: one category of geometric fact had been left on the model's side of the line. Board specs are now checked against real movement for knight, bishop, rook, queen and king, with three exemptions that stop it over-firing (highlights may be a subset of the legal moves, a piece's own square is allowed, and pawns and non-chess glyphs skip the check so a coordinate grid stays unconstrained). The gate has since caught three further genuine errors in live generation. **The limit is stated rather than implied**: this validates geometry, not chess. A castling diagram passed because the king's destination happened to sit on the rook's rank, and a caption claiming the king moves three squares is not checkable at all.

- 2026-08-17 Measured behaviour on the five live courses, before and after. The first run over the five enriched lessons produced diagrams for three, one of which was the false bishop. Three fixes followed, each from an observed failure rather than an imagined one: piece-movement validation; layout repair instead of rejection, after a lesson asked for a `chain` and then described a branching structure; and label clipping, after a 95-character node label discarded an otherwise sound graph. A fourth change was to the prompt — its worked example had been about reading a file, and the Python lesson reproduced it **verbatim**, which made it impossible to tell whether the model had reasoned or copied. Moving the example onto a subject none of the five courses covers was enough for both the Python and History lessons to produce their own. After all four, **four of five lessons produce structurally sound diagrams** and the fifth correctly produces none. The remaining honest weakness is quality rather than correctness: some boards highlight only the pieces' own squares, which is true but teaches little, and a chain of four co-proposers implies a sequence that did not exist. Those are limits of an 8B model choosing content, not of the pipeline validating it.

- 2026-08-17 Layout maths verified without adding a test runner. The frontend carries no test framework and adding one for a single module was not worth the dependency — but diagram layout is the one place in the frontend that does real arithmetic, and "it looked right in the browser" is not a claim about whether a 3-4-5 triangle actually has a right angle. `yarn check:layout` bundles the pure layout module with the esbuild that already ships inside Vite and asserts **28 properties on plain node**: the 3-4-5 triangle's angles include a 90 and sum to 180, a regular hexagon's interior angles are all 120, a tree parent sits centred over its children and children keep declared order, a chain follows edge order rather than array order, layered ranking still places every node when the graph contains a cycle, the sigmoid is monotone and crosses 0.5 at the origin, and an exponential that overflows drops its non-finite points instead of sending the whole curve to infinity. These are properties rather than pinned coordinates, so they survive a change to margins or spacing. The renderers are separately exercised from ten handwritten specs on the dev-only kitchen-sink page, which exists precisely because a wrong picture has two possible causes — a bad spec or a bad renderer — and from a lesson page those look identical.

- 2026-08-18 A feature that had never worked, and a suite that could not have noticed. The reported bug was "course certificate is non downloadable"; the finding was that it had never succeeded once, on any machine, in the entire life of the feature — `certificate_cache` held **0 rows** and `data/certificates/` **0 files**, against a database containing a fully completed and fully eligible course. `import weasyprint` is the first statement of the generator and raises `OSError: cannot load library 'libgobject-2.0-0'`, because WeasyPrint needs Pango, GLib and cairo installed as **system** libraries. `pyproject.toml` cannot express a native dependency, `uv sync` will never surface one, and the README listed `brew install whisper-cpp` and `ffmpeg` but nothing for this — so a marker cloning the repository would have hit exactly the same wall. The honest reading is that `docs/report-notes.md` had itself recorded the assumption that hid it: "WeasyPrint converts HTML+CSS to PDF **in-process — but see 2026-08-18: this framing is what hid a hard dependency on Pango/GLib/cairo, and the renderer is now fpdf2**", which is true of the Python call and false of what the Python call loads. The fix was to remove the native dependency rather than document it, since the certificate is a static layout with four substituted values and never needed an HTML engine; `fpdf2` is pure Python, so `uv sync` is now genuinely the whole setup. **Why the suite stayed green through all of it**: the only test touching the endpoint asserted a cross-user **404**, which short-circuits at the ownership check before the generator is ever called. The single assertion that would have caught it on day one — that the response begins with `%PDF` — did not exist and now does.

- 2026-08-18 An uncaught exception is not an error the user can see. The bug report arrived with a URL, a method, and an **empty status code**, and that emptiness turned out to be a second defect rather than a detail of the first. Starlette's `ServerErrorMiddleware` sits *outside* `CORSMiddleware`, so an unhandled exception propagates past the CORS layer without it ever writing `Access-Control-Allow-Origin`; the browser then blocks the response and `fetch` rejects with a bare network error carrying no status at all. A raised `HTTPException` is handled *inside* CORS and arrives intact. So in this application a 500 is not merely a worse status than a 503 — it is an **invisible** one, and the user is told nothing while the developer is told nothing. Worth generalising in the evaluation: any handler that can fail on an external dependency must convert that failure into an `HTTPException`, or the failure mode is indistinguishable from the network being down. Three smaller faults surfaced in the same area, each independently capable of producing "non downloadable": the download anchor was never appended to the DOM (Firefox ignores a click on a detached anchor) and its object URL was revoked in the same tick as the click (Safari aborts on that), with the success toast firing regardless in both cases; and `request<T>` read FastAPI's `detail` as a string when a 422 returns an array, so validation errors rendered as `[object Object]`.

- 2026-08-18 The relevance gap, which is the sharper half of the diagram story. A lesson on the perceptron had a chessboard cached against it — a knight on d4 highlighting e6 and f5, captioned "The perceptron's architecture consists of input, weighted sum, and output layers". It passed every check **including the piece-reachability gate added the day before**, because e6 and f5 are genuine knight moves. That is the finding worth the chapter: every check up to that point proved a specification was internally *consistent*, and none of them asked whether it was *relevant*. Consistent and absurd are perfectly compatible, and a validator built entirely out of internal invariants cannot tell them apart. Chess pieces now require a course that is about a board game, resolved by the same `course_profile` that already gates the pronunciation drill on `is_language_course`; boards with non-chess glyphs stay available to every subject, so only the irrelevant case is closed. A second fix followed from re-running it: one bad diagram had been sinking the whole set, discarding a sound graph because a board beside it was off-board — collateral damage against the project's own rule, since the graph made no false claim. Diagrams are now validated independently and a failure drops only itself. Verified afterwards against the live model: that lesson regenerates as two graphs, the correct primitive for it.

- 2026-08-18 Cached generation outlives the rules it was generated under. `lessons.diagram_json` is written once and kept indefinitely, which is what makes lazy generation affordable — and it means a specification stored under looser validation survives every later tightening of that validation. The perceptron chessboard would have outlived all three fixes above. `scripts/revalidate_diagrams.py` re-checks every cached specification against the *current* validator and resets the failures to NULL, which is exactly the "not yet attempted" state, so they regenerate on next open; nothing is destroyed that cannot be recreated. This is the general answer whenever validation tightens rather than a one-off `UPDATE`, and it is a consideration any cached-generation design inherits: the cache is a record of what was acceptable *then*.

- 2026-08-18 A drill that hands over its own answer. The ordering drill displayed "Step 1: …", "Step 2: …" while asking the learner to put those steps in order, because `split_steps` splits on a lookahead and therefore *retains* the marker it matched. It was solvable without reading a word of the content. That is worse than the drill being absent — it occupies the same space, claims to be practice, and tests nothing — and it would have been demonstrated in exactly that state. The markers still drive the split, since that fallback exists because the model returns steps run together on one line; they are stripped afterwards, splitting on something and keeping it never having been the same decision. **The instructive part is the fixture**: its steps were `"Step 0: do the thing."`, `"Step 1: do the thing."`, so the ordinal was their *only* distinguishing feature. Stripping it made them identical and the shuffle assertion meaningless — the fixture had encoded the bug, and a fixture that encodes a bug cannot detect it. Alongside this, the listening drill kept playing over its own score screen, because its cleanup ran on unmount and the score screen renders inside the same component.

- 2026-08-18 What the reported-bug session cost and produced. Six defects were reported from ordinary use; all six were real and five had been shipped silently. The suite grew 371 → 408, and the additions are concentrated exactly where the gaps were: PDF bytes, relevance validation, marker stripping, and the display-name split. Adding a required registration field broke **45 collected cases across two files**, every one traceable to three literals — but a further **9 would have gone quietly vacuous rather than failing**, because they already expected a 422 and would have kept passing while testing nothing at all. That distinction is worth stating in the evaluation: a test that breaks tells you where you are; a test that keeps passing for the wrong reason is indistinguishable from coverage.

- 2026-09-13 A drill that spoke its own answer, and the measurement that made the claim checkable. The listening drill played a concept's stored **definition** aloud, and a definition opens by naming the term it defines — so the audio said "Overfitting is when…" and the learner then chose "Overfitting" from the options. The root cause was structural rather than a bad prompt: `build_listen` was `build_mcq` with the `prompt` key renamed to `speak`, so whatever the reading drill asked, the listening drill said. Two sibling leaks sat in the same field of view. Multiple choice printed the same definition as a *visible* prompt and was equally solvable without thought. And the item id was `listen-<lesson>-<concept name>`, shipped beside an `options` array containing that string, so the correct index was derivable from the payload by anyone who never played the audio — a leak that had nothing to do with audio at all. **Measuring first changed the response**: rather than assert that definitions leak, `eval/j8_clue_leak_rate.py` counts it, and over the live database **26 of 27 concepts (96.3%) had a definition containing their own term**. That number is the size of the defect, and after the fix the same eval reports the clue leak rate at **0.0%**. Worth reporting because the defect had been invisible to every existing check — the suite verified that the spoken text was *not sent to the client*, which was true, and never asked whether it *named the answer*.

- 2026-09-13 Why the fix was a new pass rather than a better prompt. The obvious repair is to tell the enrichment prompt to write definitions that avoid their own term, and it is the wrong repair for two reasons. The definition serves a reader who is learning, and naming the term is what makes it teach — degrading it to make a quiz safer makes the lesson worse. And the body is cached forever, so the change would only reach lessons enriched afterwards while requiring every existing one to be regenerated, which would churn the prose this report quotes and orphan the diagrams already generated from it. `diagram_generator` had already recorded the same conclusion for its own fields. So a fourth lazy pass writes `lessons.clues_json`, a separate column, mirroring `diagram_json` in every structural respect. The deeper reason is that a clue's correctness is **negative** — it is defined partly by a sentence it must not contain — and that is not a property a prompt can promise. It needs a checker and a place to retry. `app/clue_spec.py` is the checker: a clue naming its own term is rejected at generation time, and "names" is loose about form and strict about identity — case, punctuation, hyphenation, plurals, other inflections, the multi-word acronym, and the term's head noun alone all count. Two of those rules came from tests failing rather than from foresight: `over-fitting` tokenises to two words and slipped through the phrase comparison, and the head-noun rule is what catches "Classification Threshold" described as "the threshold". This is the project's clearest instance of the pattern running in the right direction for once — the earlier defects were found by running against real data, this one by writing the test that should always have existed.

- 2026-09-13 No fallback, and the reason it is not merely safe. A concept without a clue is not asked about at all: the drill reports itself unavailable with a reason naming the missing prerequisite, and the availability message distinguishes "open a lesson to generate its content" from "the clues have not been generated yet", because they are different waits. The temptation is to fall back to the definition so the drill keeps working, and that would restore the defect precisely. The project had already written the rule that decides it — a drill that hands over its answer is worse than no drill, because it occupies the space of one, claims to be practice and tests nothing — and the ordering drill two entries above is the same ruling. The asymmetry that appears three times in this project now applies to drills as well: a missing drill is visible and honest, a broken one is invisible and worse than absent.

- 2026-09-13 Cached generation, for the third time. `clues_json` is written once and `ensure_enriched` short-circuits on stored content, so the fix cannot reach a single lesson that already exists — the same trap the diagram validator hit, where a chessboard cached under looser rules outlived every later tightening. `scripts/backfill_lesson_clues.py` regenerates the missing clues, and the decision worth recording is what it does **not** touch: only the new column. Regenerating the lesson body would also have produced clues, and would have rewritten the prose quoted in this report, invalidated the narration audio and orphaned every cached diagram, to add one field. The clue generator takes the stored body as its input, so the narrow write is available and the wide one was never necessary. Separately, the leak-rate eval reports coverage beside the rate, so a zero leak rate over three clues cannot be mistaken for a clean bill of health.

- 2026-09-13 The second dead end, which was a message rather than a mechanism. Coverage after backfilling all nine lessons was **88.9% (24 of 27 concepts)**, and the three that had none revealed a real limit: "Artificial Intelligence", "Machine Learning" and "Formal vs informal" cannot be described faithfully without their own head noun — any true account of machine learning says "learns", and the check counts an inflection as naming the term because to a listener it is. The right response was not to weaken the check, which is the only thing standing between this feature and the defect it replaced, but to accept that those concepts are not askable and have the drill say so. **What that exposed was worse than the limitation.** The first version of the availability message told the learner to "open a lesson to generate them" for every shortfall — correct when the clue pass has never run, and provably useless when it ran and rejected descriptions, because the column is then non-NULL and the cache short-circuits any retry. It was advice that could not change anything, which is the same class of failure as the drill that could not test anything. The two cases are now distinguished, and the backfill gained the matching ability to regenerate a short set and keep it **only if it covers more concepts**, so a retry can improve a lesson and can never make one worse. That recovered four lessons, 74.1% → 88.9%. One consequence is stated rather than hidden: the audio drill needs three describable concepts, and **Spanish for Beginners has two**, so that course's listening drill is correctly unavailable until another of its lessons is enriched — the availability tile names that as the fix, which is what a disabled feature with a reason is for.


- 2026-09-14 The report itself became a build, and two of its defects existed only in the output. The brief sets a hard 10,500-word ceiling across six chapters with individual caps, and both the contents list and the chapter word counts were being maintained by hand. Both had drifted, and the drift was only visible in the artefact rather than the source: `build-txt.py` had always expected a `N. [Title](#anchor)` contents format the markdown never contained, so two halves of one feature disagreed and nothing checked. Counts and contents are now generated — `wordcount.py` rewrites the headings and **fails the build** if the total exceeds the cap, `toc.py` regenerates the contents from the headings, and one `build-all.py` runs them in the only order that cannot produce a stale PDF. Somewhere to aim matters as much as the ceiling: the per-chapter targets sum to 10,400 rather than 10,500, because writing to the exact cap leaves nothing for the last round of edits. The counting convention is printed on the report's own front matter — prose only, excluding code listings, tables, captions and references — so the number is auditable rather than asserted.

- 2026-09-14 The title had drifted into five hardcoded strings, and the one that mattered was the one nobody reads. The document `<title>` in the HTML template still carried "Retention by Construction", a working title from before the draft, and Chromium takes a PDF's document metadata title from it — so every generated PDF named itself something that appeared nowhere in its pages. Contents and References were also both being handed `id="toc"`, which silently broke the sidebar's References link; two other anchors were empty strings. Every one of these was invisible from the markdown and obvious within seconds of opening the PDF. Worth recording as a pattern rather than three fixes: a source that produces four outputs needs at least one check on the output.

- 2026-09-27 Category vocabulary and model-backed Auto. Replaced the free-text Category box with a closed list served by `GET /courses/categories`, plus an "Auto" mode that asks the model to pick from that same list as the learner types. This closes two bugs that had been documented and worked around rather than fixed: a Python course filed under "Programming" never got fill-in-the-blank code questions, and a Spanish course filed under "Language" was narrated by the English voice. The existing `resolve_course_profile` had been the fix — it reads goal + category + title together because category alone could not be trusted — and the interesting part of this change is that the vocabulary is *derived from the resolver*: the language categories are built from the resolver's own keyword table rather than restating it, and tests assert that every entry resolves the way it claims. So the dropdown cannot produce a category the resolver misreads. Two design points worth carrying into the write-up: (1) "Auto" is a UI mode, not a stored value — the form previews the detected category under the field with the *reason* it matters, so the coupling to voice and question style is visible at the moment of choosing rather than discovered later; (2) nothing in the classifier raises, and an answer outside the vocabulary is rejected and replaced by a keyword match, because a prompt cannot promise "must not invent a category" — the same negative-constraint pattern as the listening clues. Verified live against llama3.1:8b on eight goals, and the request payload inspected in four states (Auto resolved, Auto still detecting, explicit choice, custom "Other"). 44 new tests.

## 5. Evaluation
_How did you test it? Quantitative (latency, accuracy, F1) and qualitative (user testing, SUS scores). What were the results?_

- 2026-09-14 The threshold result had to survive its own standard. J7 replays alternative decision rules over the same 50 labelled answers the F1 is reported on, and finds the 0.35 / 0.65 band buys 0.002 F1 for a 56% escalation rate. That is the most uncomfortable finding in the chapter and the reason the report argues that justifying a decision and testing one are different activities. Writing up the argument then exposed the flaw in it: **the comparison is in-sample**, because the band called best was selected by searching over the same labels used to report the score. It is the best rule on that fixture, not an estimate of behaviour on answers it has not seen. The report now says so where the result is given. This is the same failure the finding is about, one level up — a critique of one unvalidated choice must not itself go unvalidated — and it is worth the chapter admitting it rather than letting the negative result arrive with more authority than it has earned.

- 2026-05-04: Plan to evaluate — semantic answer-checker on 50 hand-labelled pairs (precision/recall/F1); course quality rubric on 5 generated courses; FSRS simulation of 100 cards × 30 days; user testing with 5–8 participants in Weeks 15–16.

- 2026-08-09 Evaluation infrastructure created (Phase J):
  - **J1 — Content quality**: 5 test goals × category; checks each lesson JSON for 4 structured fields; reports per-field coverage % and overall score. Run with `uv run python -m eval.j1_content_quality` (requires Ollama).
  - **J3 — Answer checker F1**: 50 hand-labelled pairs in `eval/fixtures/answer_pairs.jsonl` spanning 10 categories (definition, comparison, ml, learning-science, oop, etc.). Evaluator tested against expected verdicts; precision/recall/F1 computed overall and per category. Run with `uv run python -m eval.j3_answer_checker_f1`.
  - **J4 — FSRS simulation**: 100 synthetic cards, 30 simulated days, all-Good ratings. Measured: due count per day, average stability (grows day-over-day), state distribution (all cards eventually reach Review state), estimated retention rate. Ran successfully in <1s.
  - **J5 — Chat relevance**: 10 fixed questions per lesson, responses printed for manual 1–5 scoring. Requires running server.
  - **J6 — Latency**: embed_reference mean=0.75s (first call loads model, subsequent calls faster); evaluate_answer_correct mean=2.15s (includes Ollama LLM call for borderline scores); evaluate_answer_wrong mean=0.02s (embedding path — cosine ≤0.35 → immediate incorrect verdict); content_parser <1ms. All within acceptable bounds for a local-first, single-user prototype.
  - **Backend test suite**: 138 tests passing across all phases. Tests cover: course generation (mocked), lesson completion (idempotency), card scoping, semantic search, answer evaluator (16 labelled pairs), content parser (9 fixtures), event streaks (7 scenarios), FSRS simulation (3 interval scenarios), pronunciation (word diff).
  - **TypeScript**: 0 errors after all frontend phases (A–I).

## 6. Conclusion

_What worked, what didn't, what would you do differently, future work._

- 2026-08-09 Preliminary conclusion notes:
  - **What worked well**: The prompt-as-file pattern (Phase A) was the single highest-leverage change — extracting prompts to `.txt` files and adding structured field requirements immediately improved lesson depth without any model change. The FSRS stability-based mastery formula is principled and readable. The `content_parser` never-raise pattern eliminated an entire class of bugs that would otherwise silently corrupt downstream features.
  - **What was expensive relative to impact**: WeasyPrint certificate generation (Phase G3) took meaningful integration time for a feature that's primarily a milestone deliverable, not a core learning loop component. TTS narration (Phase D) is compelling but latency (≥5s per lesson) makes it feel slow — would benefit from async pre-generation triggered on lesson load.
  - **What I'd do differently**: Start with the behavioural event table (Phase F) much earlier — it should be part of the MVP alongside FSRS card tracking, not a later add-on. Having event data from day 1 would make the Phase H insights real immediately. Also: add a lightweight user model early, even just a `username` field — the "single-user" assumption makes it difficult to do meaningful user-comparative evaluation.
  - **Honest assessment**: The five-model stack (Llama 3.1 8b, Whisper, all-MiniLM-L6-v2, Piper TTS, FSRS-6 scheduler) works end-to-end locally. The weakest link is LLM answer evaluation — the 0.35/0.65 cosine threshold requires an Ollama call for borderline answers, which adds 2–5s latency to answer checking. The LLM judge for code fill-blank is good but slower.
  - **Future work**: Multi-user support (JWT auth, per-user FSRS state). RAG-grounded lesson content (Phase B deferred). Image generation for visual learners (Phase C deferred). Mobile-first UI. Export to Anki. Public deployment on Fly.io or Railway (SQLite + Litestream replication).
